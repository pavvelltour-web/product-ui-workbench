# Как пользоваться

Навык — инструкция агенту с дополнительными инструментами. Он не запускает автономный сервис, не создает аккаунты и не подключает платные библиотеки сам.

## Установка в свой каталог или проект

Из корня скачанного репозитория:

```bash
python scripts/install.py --host codex --project /path/to/existing-project --dry-run
python scripts/install.py --host codex --project /path/to/existing-project
```

Для Claude Code используйте `--host claude`. Для произвольного места установки используйте `--destination /path/to/new-skill-folder` вместо `--project`. Windows принимает обычный путь, например `C:/work/project`. Сначала смотрите `--dry-run`: папка проекта должна существовать, целевая папка навыка — еще нет. Скрипт не перезаписывает установленную версию и не подключает зависимости.

Установку в нестандартную папку агент не обязан обнаружить автоматически. Тогда укажите путь к `SKILL.md` в запросе либо используйте документированный каталог своего клиента.

## Начните с результата

Для полезного старта достаточно:

1. Что создаем: например, панель согласования действий агентов.
2. Что должно получиться: PNG, интерактивный прототип, код или компоненты.
3. Ограничения: существующий стек, ширины экранов, темы, зависимости.
4. Референсы или визуальное направление, если уже есть.

Реальный бренд, бизнес-план и бэкенд не обязательны. Для абстрактного исследования подходят явно синтетические данные. Если факты уже заданы, агент сохраняет их между вариантами: смена чисел мешает честному сравнению.

## Новый рабочий интерфейс

```text
Используй product-ui-workbench.
Нужна админка управления ИИ-агентами, только клиентский прототип.
Сначала сравни 2 способа работы: очередь проблем и журнал запусков.
Смоделируй короткое интервью с оператором, пометь все ответы гипотезами.
Выбери первое полезное действие и опиши состояния и мобильный порядок.
Затем найди и просмотри референсы, запиши разбор и паттерны,
переведи их в промпт и сделай 3 разных композиции.
Покажи PNG desktop/mobile, сильную сторону и компромисс каждого варианта.
```

Симуляция помогает обнаружить вопросы и сравнить решения. Она не подтверждает спрос и не заменяет интервью с реальным человеком.

Ожидаемый UX-план короткий: для кого гипотетически экран, что требует внимания, какое действие доступно, чем ограничена выборка, как открывается деталь, что происходит при ошибке и что видно на телефоне первым.

## Переработка существующего дизайна

```text
Используй product-ui-workbench. Сохрани задачи, тексты, данные и взаимодействия.
Текущий экран и 2 референса приложены.
Нужна золотая середина: плотный темный контент, оранжевое главное действие,
легкое стекло у навигации. Сделай 2 композиционно разных направления.
Не начинай заново сбор требований. Сначала сравни исходники, затем
пропиши конкретные изменения, реализуй и покажи сравнение до/после.
```

У каждого варианта должна быть видимая разница в иерархии или способе работы: очередь и деталь, повестка и контекст, этапы и выбранная сделка. Смена одного акцентного цвета — цветовой вариант, а не новая композиция.

## Точное исследование референса

```text
Разбери прикрепленный экран: композиция, роли шрифтов, отступы, цвета,
компоненты, материалы. Отдели видимые признаки от оценок размеров.
Сначала реконструируй один фрагмент для калибровки.
После сравнения сделай оригинальную адаптацию под очередь проверок.
Не переноси логотипы, изображения, личные данные и уникальные тексты источника.
```

Если нужен именно оригинальный шрифт или ресурс, агент проверяет доступность и лицензию. «Похож на системный шрифт» не равно определению точного семейства.

## Стекло и две темы

```text
Сделай один концепт в светлой и темной теме, desktop и mobile.
Сохрани одинаковые задачи и данные. Стекло нужно на плавающей навигации,
контент должен оставаться читаемым. Покажи открытый Select и Dialog,
а также непрозрачный вариант с той же геометрией.
Не называй веб-эффект точной копией нативного материала iOS.
```

Один концепт × две темы × два размера — четыре проверки одного решения. Это не четыре самостоятельных концепта. Для прозрачного текста проверяйте реальный фон в месте потребления, включая состояния успеха, ошибки и отмены действия.

## Работа без браузера или коннекторов

Передайте разрешенные скриншоты. Агент разбирает видимые признаки, пишет промпт, создает доступный ему результат и указывает границы проверки.

Если есть код, но нет способа отрендерить его, результат — реализация с непроверенным визуалом. Скриншот, сгенерированный моделью, — концепт, а не доказательство работы компонентов. Если нет ни просмотренных изображений, ни просмотра результата, визуальную оценку нельзя считать проведенной.

Как искать исходники вручную: [REFERENCE_SEARCH.md](REFERENCE_SEARCH.md).

## Библиотеки и зависимости

Сначала агент проверяет, что уже есть в проекте. Для каждого выбранного компонента различаются:

- найденный пример или документация;
- доступный исходник с лицензией;
- установленная совместимая зависимость;
- реально использованный и проверенный компонент.

Если пользователь попросил shadcn, агент должен использовать настоящий компонент с правильным API либо объяснить конкретное препятствие. Визуальная имитация не подтверждает подключение библиотеки.

Навык не дает разрешения на глобальную установку пакетов, изменение чужих проектов или публикацию. Используйте существующие разрешения и правила своего клиента.

## Как проходит итерация

1. **Зафиксировать исходную задачу и референсы.** Для нового сценария — короткий UX-план.
2. **Записать разбор и промпт до кода.** Указать решения, а не набор прилагательных.
3. **Проверить небольшой фрагмент.** Подтвердить перенос композиции и материала.
4. **Собрать экран и компонентные состояния.** Использовать выбранную реализацию.
5. **Получить настоящий рендер.** Сохранить ширину, тему и выбранное состояние.
6. **Провести два разбора.** UX: полезность, группировка, область действия. UI: шрифт, цвет, ритм, компоненты, материал.
7. **Исправить конкретные дефекты.** Например, сузить историю, убрать конкурирующий акцент, исправить текст выбранного Select.
8. **Повторить или вернуться к поиску.** Назвать оставшиеся дефекты при исчерпании согласованного числа попыток.

Техническое прохождение теста, визуальный кандидат и выбор пользователя — разные статусы. Агент не должен записывать ваше одобрение до получения ответа.

## Что просить показать

Для сравнения вариантов:

```text
Для каждого варианта дай общий PNG, мобильный PNG, ключевое открытое
состояние, отличие от исходника и один компромисс. Сведи кандидатов
в короткую таблицу. Отдельно назови, что осталось непроверенным.
```

Для проверки UX:

```text
Пройди главный сценарий в браузере: фильтр → выбранная запись → действие
→ ошибка → повтор → успех. Проверь Escape и возврат фокуса.
Покажи пустой результат и длинный мобильный экран.
Проверяй фактические суммы и подписи, а не декоративные графики.
```

Если конкретное состояние неприменимо, не нужно добавлять фиктивный контрол только ради списка проверок.

## Необязательный строгий учет через Python

Этот режим нужен для воспроизводимой истории: какой промпт предшествовал коду, какой билд попал на PNG, что изменилось после критики. Он требует подготовленных JSON и реальных файлов. Это не команда «сделай красивый интерфейс».

Для знакомства без ручной подготовки JSON начните с отдельного примера:

```bash
python scripts/demo.py --workspace /path/to/new-demo
```

Он создает собственный автономный интерфейс и манифест. Если уже есть Python Playwright и Chrome, добавьте `--chrome ABSOLUTE_CHROME`, чтобы получить реальные снимки двух размеров. Без браузера генерация примера не подтверждает визуальное качество и интерактивное поведение. Для ручного просмотра выполните `python -m http.server 4173 --bind 127.0.0.1 --directory /path/to/new-demo/generated/demo` и откройте `http://127.0.0.1:4173`; не открывайте модульный пример напрямую через `file://`.

Запускайте из корня репозитория, а рабочие файлы храните отдельно. В следующих командах `ROOT` — существующая папка запуска; входные пути относительны ей.

```bash
python scripts/design_loop.py --workspace ROOT --help
python scripts/pipeline.py --workspace ROOT --help
python scripts/pattern_loop.py --help
```

Типовой каркас, после подготовки документов по [API](API.md):

```bash
python scripts/design_loop.py --workspace ROOT prepare --id study --analysis research/analysis.json --patterns research/patterns.json --ux-plan research/ux-plan.json --prompt research/prompt.md --source-root generated/study --out runs/study-ledger.json --budget 2
python scripts/design_loop.py --workspace ROOT attach-references --ledger runs/study-ledger.json --packet research/packet.json
```

После реализации агент связывает реальные исходники через `bind-source`, создает полный манифест статической сборки и получает снимки через `render_web.py`. Для приложения с импортами недостаточно сохранить один HTML: нужны все файлы сборки. Точный синтаксис и формат входных данных приведены в API; они важнее сокращенного примера.

```bash
python scripts/render_web.py --workspace ROOT --source-manifest inputs/build.json --chrome ABSOLUTE_CHROME --out images/study-1 --mobile-full-page
python scripts/browser_probe.py --workspace ROOT --source-manifest inputs/build.json --plan research/ux-plan.json --out images/study-interactions-1 --chrome ABSOLUTE_CHROME
```

`ABSOLUTE_CHROME` — полный путь к уже установленному Chrome. Эти инструменты требуют Python Playwright. Они обслуживают локальную сборку и не заменяют проверку рабочего приложения с настоящим сервером и данными.

У проверок есть конечный заявленный охват. Они не подтверждают истинность записанного наблюдения, полный UX, красоту или доступность всего продукта. Бюджет итераций сохраняется в истории; агент не должен скрыто обнулять его после неудачи.

## После сравнения

Выберите номера кандидатов или их конкретные части:

```text
Берем композицию варианта 2, типографику варианта 1 и спокойные поверхности
варианта 3. Сначала покажи, как они работают вместе на одном экране.
После согласования собери дизайн-систему и проверь ее на другом сценарии.
```

Дальше используйте [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md). Сохраненные паттерны передают контекст и основания решений; они не превращают вкусовой выбор одного проекта в универсальное правило.
